# Local Windows signing with Certum

Status, 2026-11-06: the 3.0.0 installer, uninstaller and three project executables
have passed Windows/SignTool verification with SHA-256 and RFC 3161 timestamps.
Both files supplied in `.sign/` contain the same public certificate (PEM/DER),
not a private key. The key is provided by the cloud service. Each complete package
needs its own verification report; never label an unsigned candidate as signed.

## One-time SimplySign setup (maintainer)

1. Activate SimplySign mobile access using Certum's enrollment instructions. If
   the activation email is missing, request it from Certum or the reseller. Do not
   infer a PIN from the certificate or send activation codes to an AI assistant.
2. Install the official SimplySign mobile app and SimplySign Desktop for Windows.
3. From the Windows tray icon choose **Connect to SimplySign**, then enter the
   account name and the temporary token generated by the mobile app.
4. In **Manage certificates > Certificate list**, confirm the purchased certificate.
   It must be registered with an associated private key/provider in Windows's
   Personal store. The key stays in the cloud; do not create/export a PFX or trust
   an arbitrary root to work around an error.
5. Run the read-only preflight below. The provider may still request its PIN when
   signing. Enter it only in the provider's own dialog, not in scripts or chat.

The same store-based mechanism can support Certum hardware tokens once the vendor
driver and certificate registration are configured. The current purchase is cloud.

## Local configuration

`.sign/signing.json` is ignored and already configured on the maintainer's machine.
For another machine copy `tools/signing.example.json` and set the certificate
thumbprint. Supported fields: `thumbprint`, `store` (CurrentUser or LocalMachine),
`timestamp_url` (RFC 3161), optional `signtool_path`. There are no password fields.
SignTool is discovered in the Windows SDK x64 folders, newest version first, and
its Microsoft Authenticode signature is checked. SHA-1 identifies the certificate;
the actual file signature and timestamp use SHA-256.

From the repository root:

```powershell
& tools/sign_windows_file.ps1 -ConfigPath .sign/signing.json -Version 3.0.0 -CheckOnly
```

This checks the provider registration, associated private key, validity and code
signing usage, without signing files or changing Windows certificate trust. It
does not guarantee an online session/PIN or a successful timestamp request.

## Build and sign

Use a separate release staging directory, never your working installation with
downloaded engines/projects. The build turns off preservation of config and large
runtime dependencies. It does not publish, push, tag or contact SignPath.

```powershell
& tools/build_windows_installer.ps1 -Sign -DistRoot build/release_dist_signed
```

To use a fresh portable that was already built and audited:

```powershell
& tools/build_windows_installer.ps1 -Sign -SkipAppBuild -DistRoot build/release_dist_signed
```

`-SkipAppBuild` signs the three EXEs **in place**. Copy a candidate first if its
unsigned hashes/evidence must be retained. It is the maintainer's responsibility
to ensure the candidate's sources match the current checkout.

Order:

1. Preflight before rebuilding or touching binaries; verify Qt ICU/Host packaging.
2. Sign LocalText2Voice.exe, LocalText2VoiceEngineHost.exe and LocalText2VoiceMCP.exe.
3. Inno calls `sign_windows_file.ps1` for its uninstaller and then Setup. Its
   temporary Setup self-copies inherit the signed-uninstaller support.
4. The callback normalizes the outer installer's ProductName/ProductVersion before
   signing. Normalization must never run after signing.
5. Every signature is verified with `signtool verify /pa /all /tw` and the expected
   certificate thumbprint plus timestamp. No automatic trust or unsigned fallback.
6. Emit final SHA-256 and `signatures.json` only after successful verification.

Signed outputs go to a new timestamped folder in
`.util_instalador_y_firmas/output-signed/`. The uninstaller is kept there too, so it
can be verified. Existing output directories are rejected for signed builds.
Unsigned builds remain available without `-Sign` and are never described as signed.

The callback saves `signing.log` and copies the verified temporary uninstaller to
`signed-uninstaller/uninst-verified.exe` before Inno deletes the temporary file.
It uses only the PowerShell modules bundled with the callback's own runtime:
Inno can otherwise pass inherited PowerShell 7 module paths to Windows PowerShell
5.1, preventing `Get-AuthenticodeSignature` from loading. This isolation is local
to the callback; it does not change user/system environment variables or trust.

Before publishing, test a real signed candidate on a clean Windows machine:
install, inspect the installed EXEs and uninstaller signatures, launch GUI/MCP,
and uninstall. SimplySign must be connected during signing. A valid certificate
does not promise zero SmartScreen/AV warnings.

## Retired integration

The SignPath workflow/XML/test-trust helper were removed; generic Windows resource,
metadata and pinned-download helpers remain. Historical evidence is in Git and
[SIGNPATH_SETUP.md](SIGNPATH_SETUP.md). Account secrets/apps were not revoked
automatically. Old release reports are historical and must not be rewritten as
though those packages had been signed.
